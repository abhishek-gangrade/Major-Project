# Technical Debt & Architectural Risk Assessment: AdaptivePrep

**Project:** AdaptivePrep — Major Project, Medi-Caps University, Indore  
**Date:** November 17, 2026  
**Document:** `/docs/TECHNICAL_DEBT.md`  

---

## 1. Overview

Technical debt represents architectural shortcuts, missing safeguards, or incomplete specifications that degrade maintainability, security, or data integrity if left unaddressed. This document catalogs all identified technical debt in AdaptivePrep and outlines the concrete remediation path.

---

## 2. Catalog of Technical Debt

### TD-01: Split SQLite Database Paths
- **Issue:** `DATABASE_URL` was configured as `sqlite:///./adaptiveprep.db`. Depending on whether commands were invoked from repository root or the `backend/` directory, two separate databases (`adaptiveprep.db` and `backend/adaptiveprep.db`) were accessed.
- **Risk:** Data fragmentation; migrations run in `backend/` do not update the database file accessed when launching uvicorn from the root.
- **Severity:** High
- **Remediation:** Anchor the default SQLite database path using an absolute path derived from the project root in `backend/app/core/config.py`.

### TD-02: Missing Vite Environment Declarations
- **Issue:** `frontend/src/vite-env.d.ts` was not created, causing TypeScript compiler `tsc` to fail on `import.meta.env.VITE_API_BASE_URL`.
- **Risk:** Breaks automated production builds (`npm run build`).
- **Severity:** High
- **Remediation:** Create `frontend/src/vite-env.d.ts` containing `/// <reference types="vite/client" />`.

### TD-03: Transient Recommendations Without Persistent Audit Log
- **Issue:** Recommendations generated by `adaptive_engine.select_next_candidate` were delivered directly to the client via HTTP response without saving an audit record.
- **Risk:** Violates Section 4 of the architectural specification ("Step 12: Save the recommendation record and relevant learner-state snapshot"). Inability to conduct retrospective audits or verify why a question was selected at time $t$.
- **Severity:** High
- **Remediation:** Create `recommendation_logs` database table storing recommendation ID, user ID, question ID, question version, target topic, difficulty, learner state snapshot ($A, R, D, E$ values), algorithm version, and timestamp.

### TD-04: Binary `is_active` Question State Lacks True Publishing Lifecycle
- **Issue:** Questions only possessed `is_active: bool`. There was no transition pipeline between Draft, Review, Published, and Archived.
- **Risk:** Incomplete questions could be drafted and accidentally published directly to students without review.
- **Severity:** Medium
- **Remediation:** Add `status` field (`draft`, `in_review`, `published`, `archived`), `version`, `subtopic`, and `concept_tags` to `Question` model.

### TD-05: Missing User Profile & Settings Management
- **Issue:** Frontend lacked a Settings view. Users could not view or update profile preferences, graduation year, or manage research participation consent.
- **Risk:** Incomplete UI navigation relative to project requirements (Section 8: "5. Settings").
- **Severity:** Medium
- **Remediation:** Implement `Settings.tsx` with user profile editing and research consent toggle, with supporting `PATCH /api/v1/auth/profile` endpoint.

### TD-06: Lack of Auth Rate Limiting
- **Issue:** `/api/v1/auth/login` and `/api/v1/auth/register` endpoints lacked request throttling.
- **Risk:** Susceptibility to brute-force credential stuffing.
- **Severity:** Medium-High
- **Remediation:** Implement an in-memory client-IP based rate limiter middleware for sensitive auth routes.

### TD-07: Untracked Attempt Start Timestamps & Duplicate Submissions
- **Issue:** Attempts recorded client-reported `time_taken_seconds` but lacked an explicit session-bound `started_at` timestamp and idempotency token.
- **Risk:** Double-clicking "Submit" or network retries could record duplicate attempts for the same question.
- **Severity:** Medium
- **Remediation:** Add duplicate submission prevention in `PerformanceService.record_attempt` (rejecting identical submissions for the same question within a 5-second window).

### TD-08: Research Module Lacks Live Student Diagnostic Flow
- **Issue:** The research module included evaluation dataset statistics and CSV export, but lacked a dedicated UI workflow for students to take a 10-question baseline diagnostic pre-test or post-test.
- **Risk:** Hindered practical demonstration of the research evaluation methodology to professors.
- **Severity:** Medium
- **Remediation:** Implement interactive diagnostic assessment capability in the practice/research module.
